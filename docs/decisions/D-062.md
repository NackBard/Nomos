# D-062. Каталог правил без версии в manifest; языковые пакеты регистрируются данными package.json

Ответы пользователя в начале этапа 18 (2026-11-07), закрывают открытые вопросы 16 и 17.

- **Вопрос 16: версии каталога в manifest нет.** Ядро и языковой пакет могут быть собраны с разными каталогами (D-056). Новое правило ядро показывает по `message.text`, правило без детектора — по `supportedRules`, неизвестный ключ шаблона — снова по `message.text`. Не закрыт был один случай: ключ тот же, а аргументы другие — ядро подставило бы аргументы нового анализатора в свой старый шаблон. Номер версии этого не исправляет: по нему не видно, какие шаблоны изменились. Поэтому правило spec (`spec/l10n.md`): ключ не меняет набора аргументов; другой набор — новый ключ, старый удаляется; формулировку при тех же аргументах можно менять. `npm run spec-json` сравнивает новый каталог с `extension/rules.json` и ничего не пишет, если у ключа изменились аргументы. Контракты не меняются, manifest остаётся 1.2.0.
- **Вопрос 17: регистрация — данные `package.json`.** Языковой пакет — расширение VS Code без `main`: оно никогда не активируется и кода не содержит. Его записи реестра лежат в `package.json` под ключом верхнего уровня `nomos` (`{"nomos": {"analyzers": [ … ]}}`, формат записи — как в `bundle/analyzers.json`, D-046), а анализатор — в папке `bundle/` пакета. Ядро собирает реестр из `vscode.extensions.all`, `${bundle}` записи — папка `bundle` её пакета, и пересобирает его по `vscode.extensions.onDidChange`. Свой `bundle/analyzers.json` ядро читает по-прежнему: им пользуются разработка и e2e из исходников.
  - Отвергнуто: API ядра, который пакет вызывает при активации — в пакете появился бы код, ему нужна была бы активация, а `check-boundary` пришлось бы проверять ещё и его.
- **Как ядро предлагает поставить пакет.** Ядро несёт список известных пакетов `packs.json`: имя расширения пакета и `files` его анализаторов. Он пишется сборкой из manifest анализаторов, как `rules.json` из spec, — это данные, а не код, `check-boundary` его не касается. Id пакета — издатель ядра, точка, имя из списка. Если в папке без `nomos.json` есть файлы известного пакета, а сам он не установлен (или выключен), ядро показывает уведомление «Nomos может анализировать эти файлы, если поставить пакет X» с кнопками «Поставить» (`workbench.extensions.installExtension`) и «Больше не спрашивать» (запоминается в `globalState` для пакета). После установки анализ запускается заново. Без единого пакета ядро ставится, а строка состояния говорит, что анализировать нечем, и называет пакеты для найденных файлов.
  - Отвергнуто: поиск пакета в Marketplace по тегу — нужна сеть, не работает офлайн и с другими галереями (Open VSX).

- **Сборка.** `npm run package` (`extension`) собирает анализаторы в `bundle/` и пишет `packs.json`, потом в `dist/` — ядро без `bundle/` (`nomos-<версия>.vsix`, одно на все платформы) и по пакету на папку анализатора: `nomos-csharp`, `nomos-go`, `nomos-typescript` (TypeScript и JavaScript), `nomos-python`, `nomos-java`, `nomos-kotlin`, `nomos-ruby`. Под цель (`--target`) собирается только `nomos-go`: остальные пакеты не содержат родных программ. Версия, издатель, лицензия и `engines` пакета берутся из `package.json` ядра, зависимость — `<издатель>.nomos`. `--only` собирает выбранные части, `--bundle-only` — только `bundle/` и `packs.json`. Ядро на Windows весит 0,5 МБ вместо 9 МБ; пакет Kotlin — 57 МБ.
- **Проверка.** `npm run e2e -- <папка> --packs` ставит в профиль ядро и пакеты из `dist/`, и тест требует, чтобы каждый анализатор запустился из папки своего пакета, а не из `bundle/` ядра. На папке с Go, TypeScript, JavaScript, Java и Kotlin это проходит на Windows. Предложение поставить пакет проверено модульными тестами, в e2e его не нажать.

Новых зависимостей нет.
