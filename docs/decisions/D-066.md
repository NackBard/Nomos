# D-066. Свободные функции модуля на диаграмме классов — класс «utility»

Просьба пользователя (2026-11-13, ручная проверка): выгрузка UML модуля `NomosRuby::Metrics` вышла пустой. В нём нет типов, только функции модуля (`def self.x`), а диаграмма классов показывала одни типы. Так же пусты модули из одних функций в Go, Python, TypeScript и Kotlin.

Решение: свободные функции модуля (функции без `type`, кроме `lambda` и `accessor`) на диаграмме классов — один класс со стереотипом «utility» и именем модуля, их операции статические. «utility» — стандартный стереотип UML для класса, у которого только статические члены; так же рисуют модули Ruby с функциями и модули Python. Правило общее для всех языков, поэтому контракт facts и анализаторы не меняются — только `spec/structure.md` и диаграмма в расширении.

- **Где.** Класс появляется на диаграмме модуля, пары модулей (функции обоих) и всего проекта (по классу на модуль с функциями). На странице графа в режиме UML точки-функции модуля сворачиваются в этот класс, их связи переходят на него; без UML граф прежний.
- **id.** `<id модуля> «utility»`: id модуля занят самим модулем, и граф принимает такой id за модуль (D-061); пробела и кавычек-ёлочек в id фактов не бывает.
- **Отвергнуто.** Писать модуль Ruby отдельным типом в facts: нужен новый id, новая версия контракта и правка анализатора, а выгода только у Ruby. Рисовать «utility» только у модулей без типов: тогда у модуля, где есть и классы, и функции, функции на диаграмме пропадали бы.

Миксины Ruby уже на диаграмме: анализатор пишет их типом `trait`, а `include` — ребром `inheritance`, это реализация (D-061).
