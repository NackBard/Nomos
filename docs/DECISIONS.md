# Журнал решений

Каждая запись: что решено и почему. Новые записи добавляются в конец.

## D-001. Модуль C# — это namespace

Метрики Мартина и слои требуют единицы «пакет». Сборка слишком крупна, а .csproj без MSBuild не всегда виден. Namespace есть всегда и обычно отражает задуманное деление. Адаптер другого языка сам определяет модуль: файл, пакет, директорию.

## D-002. Языки, парадигмы и категории — строки

Перечисления потребовали бы менять `Abstractions` при каждом новом языке, что нарушает главное требование. Цена — опечатка в конфиге не ловится компилятором, поэтому неподдерживаемая парадигма даёт предупреждение в отчёте.

## D-003. Без MSBuildWorkspace: одна компиляция на все исходники

`Microsoft.CodeAnalysis.Workspaces.MSBuild` тянет MSBuild и Build.Locator и требует установленного SDK и выполненного restore у анализируемого проекта. Вместо этого `.sln`, `.slnx` и `.csproj` разворачиваются в папки проектов, а все `.cs` компилируются вместе со ссылками на сборки `System.*` текущего рантайма. Добавляется файл с типовыми `global using`, иначе код с `ImplicitUsings` не разрешался бы.

Следствия, принятые сознательно:

- типы из NuGet не разрешаются, и такие символы работают по именам; число таких ссылок выводится в заметки отчёта;
- одноимённые типы из разных проектов сливаются в один;
- условная компиляция и `#if` не вычисляются.

Анализ работает без сборки проекта, что важно для CI и IDE. Точность можно поднять позже отдельным адаптером или опцией, не меняя ядро.

## D-004. Записи вместо классов с visitor для IR

IR — это `record`, обход идёт через `Children`. Новый тип узла не требует правки интерфейса visitor во всех анализаторах, а старые анализаторы видят его потомков.

## D-005. Обязательное объяснение на уровне API

`AnalysisContext.Report` бросает исключение при пустом объяснении, а `Confidence` — обязательный параметр. Требование «эвристика не выдаётся за вердикт» обеспечено типами, а не договорённостью. Точная метрика (число строк) может иметь High, но текст говорит, что порог — соглашение.

## D-006. Анализатор и метрика — один контракт

Отдельного `IMetricProvider` нет: анализатор отправляет `Metric` через тот же контекст. Метрики и выводы из них почти всегда считаются вместе.

## D-007. Отдельный проект и категория Paradigm

В ТЗ семь проектов анализаторов по категориям, но правила концепции 3 (инкапсуляция, чистота и другие) ни в одну не входят. Добавлен `Nomos.Analyzers.Paradigms` с категорией `Paradigm`. Его namespace — `Nomos.Analyzers.Profiles`, потому что иначе он перекрывает класс `Paradigms`.

## D-008. ControlFlow и DataFlow как запросы, без графов

В ТЗ они указаны «по мере необходимости». Текущим анализаторам хватает цикломатической сложности, вложенности, поиска недостижимого кода и нечувствительного к потоку набора чтений и записей. Полный CFG с базовыми блоками был бы кодом без потребителя. Он понадобится для taint-анализа в Security.

## D-009. Вложенность, размер функции и класса не дублируются в Structural

ТЗ называет их и для CleanCode, и для структурной парадигмы. Два анализатора дали бы двойной штраф за одно и то же. CC001, CC003, CC004 и другие размечены несколькими парадигмами, а Structural добавляет только своё: goto, глобальное состояние, размер модуля.

## D-010. Обход иерархии не считается вложенным циклом

`foreach (var t in module.Types) foreach (var c in t.Callables)` линеен по общему размеру, но наивная оценка давала O(n²), и на коде самого Nomos 113 методов получили ложную «сложность». `Estimator` отслеживает имена, связанные с элементом внешней итерации, и обход их содержимого не умножает. Рекурсия по членам (обход дерева) считается линейной. Ошибка в другую сторону тоже возможна: `foreach (x in a) foreach (y in x.Shared)` с общим большим списком будет недооценён. Цена принята, потому что шум убивает доверие к отчёту сильнее, чем редкий пропуск.

## D-011. Функциональный профиль для C# выключен по умолчанию

`DefaultParadigms` адаптера: `oop`, `structural`. На обычном объектном C# правила FUN003 (мутабельность) сработают почти на каждом классе. Включается через `languages.csharp.paradigms`.

## D-012. Клоны токенов с порогом 100

MNT003 использует rolling hash по нормализованным токенам: находит клоны типов 1 и 2. Порог 60 ловил шаблонный код объявлений анализаторов; 100 близко к значению по умолчанию в PMD CPD. PRN006 дополняет его сравнением формы IR на уровне методов.

## D-013. Формула здоровья с экспонентой

Линейный штраф уходит в ноль на больших проектах, а без нормировки балл зависит от размера. См. раздел «Здоровье» в `ARCHITECTURE.md`. Все коэффициенты вынесены в конфиг.

## D-014. Детерминированный вывод

Отчёт не содержит времени и абсолютных путей, порядок фиксирован. Это условие golden-тестов и полезно для diff в CI. Версия инструмента в отчёте есть: при её смене golden-файлы обновляются осознанно.

## D-015. Находки и отчёты на английском

XML-документация требовалась на английском, а сообщения находок живут рядом с кодом. Локализация сообщений отложена. Документация проекта на русском, как и постановка задачи.

## D-017. Tree-sitter без нативной привязки

`Nomos.Languages.TreeSitter` содержит `ISyntaxNode`, `ITreeSitterParser` и `TreeSitterAdapterBase`. Привязка к нативной библиотеке отсутствует намеренно: она добавила бы зависимость без единого использующего языка. Контракт проверен тестом на поддельном парсере.

## D-018. Каталог анализаторов генерируется из исходников

`docs/ANALYZERS.md` построен по атрибутам `[Analyzer]`, чтобы описание не расходилось с кодом. Этап 0 просил список заранее, но фактический список стабилизировался только вместе с реализацией.

## D-020. Языко-родные анализаторы вместо единого .NET-ядра

**Решено.** Каждый язык анализируется самостоятельной программой, написанной на этом языке или с его родными инструментами (C# — Roslyn, Python — `ast`, TypeScript — компилятор TS). Единого ядра с общим IR, разбирающего все языки, не будет. Общим остаются контракты (`contracts/`), спецификации (`spec/`) и тесты соответствия (`conformance/`). Расширение VS Code (`extension/`) — только потребитель контрактов.

**Почему.**

- Точность. Родной инструмент знает язык лучше любого общего IR: разрешение имён, типы, условная компиляция, версии языка. Общий IR вынуждает терять различия или раздувать модель (см. D-003: символы без разрешения, `OpaqueExpression`).
- Поддержка. Новая конструкция языка требует обновить только анализатор этого языка, а не общий слой и всех его потребителей.
- Независимость. Анализатор другого языка пишется людьми, знающими этот язык, без знакомства с .NET.
- Граница ответственности. Расширение не содержит логики языка, поэтому не становится вторым ядром.

**Цена.** Формулы метрик и правила дублируются в каждом анализаторе; расхождения незаметно накапливаются. Компенсация:

- формулы описаны один раз в `spec/metrics.md`, правила — в `spec/rules/*.yaml`;
- `conformance/` содержит эталонные фикстуры на каждом языке с ожидаемыми facts; пройти его обязательно, эталоны считаются вручную, а не берутся из вывода анализатора;
- `parity` в `case.json` требует равенства метрик у эквивалентных сущностей разных языков;
- контракты версионируются, изменения только явным повышением `schemaVersion`.

Остаточный риск: метрики, зависящие от токенизации (Halstead, MI), различаются между языками; для них задан широкий допуск, и они трактуются как порядок величины.

**Следствия для существующего кода.** Проекты `src/` и `tests/` не удаляются. `Languages.CSharp`, `Analyzers.*`, `Core`, `Graph`, `Reporting` и `Cli` переезжают в `analyzers/csharp` на этапе 2 (раздел «Миграция» в `ARCHITECTURE.md` и `ROADMAP.md`). D-017 (Tree-sitter без привязки) отменяется: проект `Languages.TreeSitter` удаляется на этапе 2, поскольку мультиязычного разбора больше нет. D-002 (строки вместо enum) сохраняется как принцип контрактов. D-005 (обязательное объяснение), D-014 (детерминизм) и D-015 (английский текст находок) переносятся в контракты: SARIF-профиль требует `confidence` и `explanation`.

## D-021. Платформа даёт статистику, а не вердикты

Пороги в `spec/rules` — чувствительность детектора («с какого значения о значении стоит сообщить»), а не граница приёмки. Сырое значение всегда присутствует в facts. Оценка A–F и опции `--fail-on`, `--min-score` убраны (в коде .NET удалены до этого решения); код возврата анализатора и CI-режима (этап 8) не зависит от числа находок и значения балла. Балл здоровья остаётся числом с объяснением в `facts.health`.

## D-022. Протокол: SARIF пишется в файл, facts идёт в stdout

Команда `analyze` печатает facts в stdout; при `--sarif <файл>` дополнительно записывает SARIF в указанный файл и сообщает путь в `checks.sarifFile`. Отдельной третьей команды нет. Причина: SARIF — потенциально большой документ, а клиенту (расширению, CI, GitHub Code Scanning) удобнее иметь файл; facts остаётся единым ответом процесса. Балл здоровья вычисляет анализатор, потому что у него есть и метрики, и находки; расширение его не считает.

## D-023. Принятые мной решения при написании контрактов

- `schemaVersion` — строка semver, начальное значение `"1.0.0"`, проверяется как `const` в каждой схеме. Версия схемы также лежит в `$id` и в `x-contractVersion`.
- Связь «runtime или type-only» вынесена в отдельное поле `phase`, а `kind` ограничен значениями `import`, `inheritance`, `call`, `type-ref`: так одна и та же связь классифицируется по двум независимым осям.
- Идентификаторы сущностей — родные квалифицированные имена языка, стабильные между запусками; сопоставление между языками идёт через `parity` в `case.json`, а не через единые id.
- Языко-специфичное правило получает префикс с кодом языка, формат `CS.NAM001`. Прежнее правило `CC005` переименовано в `CS.NAM001`, поскольку проверяет конвенции именования .NET.
- Активация парадигмы по признакам задана в `spec/paradigms.md`: `oop` — наличие классов, `functional` — функции высшего порядка или чистые функции или не менее трёх лямбд, `structural` — свободные функции или ветвления. Порог «три лямбды» — эвристика, чтобы LINQ не включал функциональный профиль на обычном C# (продолжение D-011).
- Метрики графа (Ca, Ce, циклы, blast radius) считаются над единицами «тип или свободная функция», все виды рёбер и обе фазы равноправны, рёбра на внешние цели не участвуют. Дальнейшее уточнение (учитывать ли `type-only` отдельно) — открытый вопрос.
- Вложенные функции и лямбды входят в сложность охватывающей функции.
- Harness conformance предлагается писать на TypeScript/Node: те же инструменты нужны расширению, там есть зрелые валидаторы JSON Schema.
- Имя продукта — Nomos (D-024); файл рабочей области — `nomos.json`.
- Физический перенос .NET-проектов в `analyzers/csharp` на этом шаге не выполнен: он ломает сборку, `Directory.Build.props`, `slnx`, golden-тесты и команды из README, а код сейчас не пишется. Перенос — первая задача этапа 2.

## D-024. Продукт называется Nomos

Заменяет имя DeepCode.Analizer (D-019) и снимает прежний вопрос об имени. Применено везде:

- контракты и документы: файл рабочей области `nomos.json`, схема `contracts/nomos.schema.json`, ключ отпечатка SARIF `nomos/v1`, пример имени анализатора `nomos-csharp`, `$id` схем в виде URN `urn:nomos:contracts:<версия>:<имя>`;
- .NET-код: решение `Nomos.slnx`, проекты и пространства имён `Nomos.*` (было `DeepCode.Analizer.*`), команда CLI `nomos`, директивы `nomos-disable`, атрибут `[NomosSuppress]`, класс `NomosConfig`, переменная `NOMOS_UPDATE_GOLDEN`, папка отчёта `nomos-report`. Сборка и все тесты проходят, golden-файлы перегенерированы.

Проекты по-прежнему лежат в `src/` и `tests/`; перенос в `analyzers/csharp` остаётся этапом 2. Корневая папка репозитория пока называется `DeepCodeAnalizer`.

Известная коллизия: имя `nomos.json` сейчас означает два разных файла. В корне репозитория это конфиг текущего .NET-инструмента (бывший `deepcode.json`: языки, пороги, подавления), а `contracts/nomos.schema.json` описывает файл рабочей области для расширения. Слияние или разделение (например, `nomos.json` для рабочей области и секция `analyzerOptions`) решается на этапе 2.

## D-025. `$id` схем — URN, а не URL

`$id` имеет вид `urn:nomos:contracts:1.0.0:manifest` (имена: `manifest`, `facts`, `rule`, `nomos`, `conformance-case`). Схемы лежат в репозитории, валидаторы подгружают их оттуда, поэтому адрес в сети не нужен; URN не зависит от домена, который нам не принадлежит. Внутри схем используются только внутренние ссылки (`#/$defs/...`), так что формат `$id` на них не влияет. Если появится собственный домен для публикации схем, `$id` меняется вместе с `schemaVersion`.

## D-026. Harness conformance: Node, правила сравнения, границы первых случаев

**Решено.** `conformance/runner` написан на TypeScript и запускается Node 22.18+ без сборки (типы стираются самим Node, `tsc` нужен только для проверки). Зависимости (`conformance/runner/package.json`, версии закреплены):

| Пакет | Версия | Зачем |
|---|---|---|
| ajv | 8.17.1 | валидация по JSON Schema 2020-12, метавалидация контрактов |
| yaml | 2.8.1 | чтение `spec/rules/*.yaml` перед проверкой по `rule.schema.json` |
| typescript, @types/node | 5.9.2, 24.3.0 | только `npm run typecheck`; в рантайме не участвуют |

Команды: `npm run validate` (контракты, `spec/rules`, случаи), `npm run run -- --analyzer "<язык>=<команда>"`, `npm test` (самопроверка сравнения), `npm run selftest` (эхо-анализатор отдаёт эталон; проверяет путь успеха harness, не анализатор).

**Как сравниваются facts** (`runner/src/compare.ts`):

- Сущности (файлы, модули, типы, функции) сопоставляются по `id`; лишние и отсутствующие — ошибки. Метрики сравниваются только те, что указаны в эталоне; лишние метрики в выводе не ошибка.
- Рёбра зависимостей сравниваются по `(from, to, phase)`. **`kind` не сравнивается**: `spec/metrics.md` не определяет, когда ребро — `call`, а когда `type-ref`, и эталон, посчитанный вручную, зависел бы от выбора реализации. Внешние и stdlib-рёбра не сравниваются. Открытый вопрос: определить `kind` в spec и включить его в сравнение.
- `cycles` сравниваются как множества компонент.
- `paradigmEvidence` точны только в случаях, где `covers` содержит `paradigmEvidence`; в остальных эталон — подмножество. `skippedRules` в эталоне — подмножество вывода; полноту записей `paradigm-not-detected` проверяет общая проверка по `supportedRules` манифеста.
- Идентификаторы функций в эталонах C# — без сигнатуры (`Metrics.Basics.Straight`), перегрузок в случаях нет. Неявные конструкторы в `functions` не попадают. Это договорённость для C#, которую нужно закрепить в spec при реализации анализатора.

**Границы первых случаев.** Исходники C# в случаях намеренно используют только поля и полностью квалифицированные имена (без `using`, без методов там, где метод не нужен), чтобы эталон не зависел от неоднозначных мест spec. В `paradigm-evidence` проверены только признаки `oop.*`: у `fp.pure-functions` нет проверяемого определения («по анализу самого анализатора»), а любой модуль с методами имел бы этот признак. Случаи `fp.*`/`str.*` добавляются после уточнения в `spec/paradigms.md`. Ребро `type-only` в случаях отсутствует: в C# такого понятия нет. Схема `case.json` не содержит поля для исключений по языку (его упоминает `conformance/README.md`): это предложение изменить контракт, отдельное решение. Все случаи пока только на C#; случай с одним языком не проверяет parity, поэтому полноценными conformance-случаями они станут со вторым языком (этап 7).

**Частичный результат.** Файл с синтаксическими ошибками помечается `parsed: false`, в `diagnostics` появляется запись `warning` с `file` и кодом `syntax-error`, анализатор завершается с кодом 4, остальные файлы разобраны как обычно. **Производительность.** Анализ самого Nomos (49 файлов, 233 типа, 1539 зависимостей) занимает около 10 с вместе с запуском; blast radius не является узким местом на таком размере и не оптимизирован. На существенно больших проектах это не проверено.

**Охват `measured`.** Из примерно тридцати правил с числовыми порогами поле заполняется у одиннадцати (D-029). На самоанализе Nomos поле есть у 82 из 272 результатов. Остальные правила (ALG, PRN, STR, PAT и др.) дорабатываются по одному.

## D-033. Лямбды не активируют функциональную парадигму; парадигму нельзя объявить явно

Закрывает открытый вопрос 6, заменяет порог «три лямбды» из D-023. Решение принял пользователь.

**Активация.** `fp.lambdas` записывается в facts как статистика, но `functional` активируют только `fp.higher-order` и `fp.pure-functions`. На самоанализе Nomos (обычный объектный код с LINQ) прежнее правило активировало парадигму в 16 модулях из 16 и ничего не различало; новое — в 7 из 16. Порог на плотность отвергнут: это ещё одно подбираемое число, а на LINQ-коде плотность всё равно высока. Парадигма по-прежнему активируется одной функцией с признаком; порог на их долю можно ввести позже, если этого окажется мало.

**Объявление.** Явного объявления парадигмы нет ни в `nomos.json`, ни в коде: конфигурация только отключает парадигму для языка (`spec/paradigms.md`), контракт не меняется. Иначе правила ООП могли бы сработать на модуле без классов. К вопросу можно вернуться, когда появится реальный случай.

Новых golden-файлов и эталонов не потребовалось: functional для C# выключен по умолчанию (D-011), а случаи conformance этого условия не задевали. Условие закреплено юнит-тестом в `Nomos.Facts.Tests`.

## D-034. Этап 4: активные и включённые парадигмы, контракт 1.1.0, метрики стиля

**Два механизма.** Активность парадигмы вычисляется по коду, включённость задаёт конфигурация или умолчание языка (D-011). Раньше они смешивались в двух местах. **Контракт 1.1.0** (минорная версия: необязательное поле). В `modules[]` добавлено `activeParadigms`. **Метрики стиля.** `hofOrder`, `lambdaNesting`, `typeTests` определены в `spec/metrics.md` и выводятся в `functions[].metrics` всегда, даже когда правила FUN выключены: сырые значения не должны зависеть от порога или парадигмы. Внутренняя метрика `hof-order` переименована. Код вынесен в `CallableMetrics`, размеры файлов и модулей — в `SizeMetrics`.

**`measured`.** Заполнено для всех правил этапа с порогами: FUN005, OOP003, STR003. Охват `measured` у ALG, PRN, PAT и остальных дорабатывается на их этапах. Harness сверяет `loc` с модулем и `lines` с файлом результата.

**Найдено эталоном и исправлено.**

- `oop.inheritance` не учитывал записи.

- STR003 сравнивал порог с оценкой `LinesOfCode` из IR (сумма строк типов), а не с `loc` из spec, а для файла считал на строку больше при завершающем переводе строки. Оба значения теперь совпадают с facts.

Текст таблиц `spec/paradigms.md` приведён к коду для `oop.classes` (свойства считаются) и `fp.immutable-types` (нужно состояние, а не любые члены).

**Harness.** Проверка `skippedRules` была только для `oop.classes` и только в одну сторону. Теперь таблица активации читается из `spec/paradigms.md`, и в каждом случае проверяется, что `activeParadigms` следуют из признаков, что правило без активной парадигмы имеет запись и что правило с активной её не имеет. Список линейных операций языко-зависим и принадлежит анализатору, spec задаёт только смысл; случай `complexity-estimates` от него не зависит и взаимной рекурсии не содержит.

Имя и расположение заданы условно, как у `expected.sarif.json`. Поле `schemaVersion` стало `enum`, старые случаи остаются 1.0.0. Заодно уточнён смысл `expectSarif`, который раньше ни разу не использовался: сравниваются только правила из `covers`, иначе в каждый эталон пришлось бы вписывать находки всех прочих правил. Теперь `SpecRules` читает `requires`, `Program` определяет доступные входы, facts пишут запись на весь запуск, harness проверяет её в обе стороны. Golden получил запись у MNT004.

В остальном детекторы совпали с ручными эталонами с первого запуска; единственное расхождение (строка `new Box()` в `complexity-estimates`) оказалось ошибкой подсчёта в эталоне и исправлено там, по тексту файла.

Выигрыш важен лишь на бо́льших графах; замеров больше 3000 типов нет. Память квадратична по числу типов: около 1 МБ на 3000, 125 МБ на 30 000.

Правило CC002 считает структуру и методы, но `lines` у типа — только его объявление, потому что методы лежат вне него.

## D-039. Этап 8: отчёты и запуск без IDE

Закрывает открытый вопрос 2: отчёты строятся из facts и SARIF, решение принял пользователь. Новый пакет `ci/` на TypeScript, запускается Node 22.18+ без сборки, как harness. Он не знает языков: `check-boundary` к нему не применялся, но кода по языкам в нём нет, тест ведёт несуществующий язык `toy`. Зависимость — `ajv` 8.20.0, та же версия, что в harness и расширении (все три подняты с 8.17.1 ради уязвимости): facts и `nomos.json` проверяются по схемам. `Nomos.Reporting` и его тесты удалены: заменены, и C# не должен владеть отчётом по всем языкам.

**Baseline** — файл `{ baselineVersion, findings }` по отпечатку `nomos/v1`. Это собственный файл `ci`, его никто другой не читает, поэтому в `contracts/` он не вынесен. Сравнение — мультимножества: одинаковые находки в одном файле имеют один отпечаток, и исчезновение одной из двух остаётся изменением. Отпечаток не зависит от строки, но зависит от файла и текста сообщения: переименование файла или изменение числа в сообщении выглядит как «исчезла и появилась». Сообщения вида `spans 52 lines` меняются вместе с кодом, и это честное ограничение.

**Код возврата** не зависит от находок, балла и новых находок (D-021). Частичный результат анализатора (код 4) не ошибка: отчёт его показывает. Единственная ошибка по сути — анализатор не завершился: тогда отчёт записан без него, а код 1, иначе CI выдал бы неполный отчёт за полный.

**CI репозитория.** Запуск `ci` на самом Nomos и выгрузка папки `.nomos` как артефакта; `e2e` по-прежнему вне CI. Действия обновлены до версий без устаревшего Node 20, `yaml` в harness поднят до 2.9.1 ради закрытия уязвимости.

**Не сделано.** Выгрузка в GitHub Code Scanning не подключена, решение пользователя (D-040).

## D-041. Цвет узла графа — глубина зависимости

Уровень узла в панели графа — длина самого длинного пути по показанным зависимостям: 0 у узла, который ни от чего не зависит, участники одного цикла получают один уровень. Считается в `extension/src/core/views.ts` из рёбер графа, в контракты и `spec/metrics.md` не входит: это способ отображения, а не метрика, и в отчёты он не попадает. Цвет не оценка: глубокий узел не хуже мелкого.

Выбран этот смысл, а не `layers` из `nomos.json`: те заданы не везде и привязаны к модулям, а глубина есть у любого языка и у обоих графов. Красный оставлен циклам и стал обводкой, чтобы цикл не скрывал уровень. Цветов восемь, всё глубже седьмого уровня сливается в «7+».

Узлы крупнее и при отдалении сохраняют экранный размер. На графах больше 60 узлов подписи при масштабе меньше 1 показываются только для узла под указателем и его соседей: на самоанализе (267 типов) иначе они слипаются.

Проверено глазами: пользователем в VS Code и на скриншотах страницы с реальными facts в тёмной и светлой темах.

## D-042. Граф открывается рядом с кодом, как отдельная поверхность

Значок в боковой панели — свой (`media/icon.svg`, временный). Открытие представления Nomos показывает граф на отдельной вкладке рядом с кодом, не забирая фокус, и запускает анализ, если результатов ещё нет. Дерево находок остаётся в боковой панели. Команда `nomos.openGraphWindow` (кнопка на вкладке графа) переносит его в отдельное окно VS Code штатной `workbench.action.moveEditorToNewWindow`.

Отдельное окно не стало поведением по умолчанию: оно открывалось бы поверх основного при каждом клике по значку.

Граф теперь обновляется после каждого анализа: раньше данные приходили только при открытии и переключении уровня. Скрытая страница получает их при показе, потому что без размеров вписать граф нельзя.

## D-043. Код открывается в соседней группе, дерево парадигм читается сверху вниз

Клик по узлу графа открывает код в группе рядом с графом: в предыдущей, а если граф первый, то в следующей. Единственная группа делится. Раньше код шёл в первую колонку, поэтому при разделённом экране он мог оказаться не рядом, а из отдельного окна всегда уходил в главное. Выбор считает `neighbourGroup` по `tabGroups`: группы отдельного окна идут в том же списке, поэтому из него открывается последняя группа основного окна. Вкладка предварительного просмотра переиспользуется, клики по узлам не копят вкладки.

Дерево «Paradigms and Skipped Rules» теперь идёт по цепочке язык → стиль → модуль, а не двумя параллельными списками. Причина пропуска — сама строка дерева словами анализатора, правила с их названиями лежат под ней; код причины и текст только в подсказке показывали меньше, чем есть в facts. Модуль без своих пропусков говорит об этом отдельной строкой: на самоанализе таких 7 из 15 у C#, и пустота выглядела как потерянные причины. Названия правил берутся из каталога SARIF всех запусков: контракты не менялись, а Go не перечисляет правила, которых не реализует.

## D-044. Граф раскладывается по колонкам глубины

Силовая раскладка заменена слоистой: колонка узла — его глубина из D-041, слева то, от чего зависят, справа зависящие. Порядок внутри колонки подбирается по среднему положению соседей, это убирает большую часть пересечений. Расположение теперь повторяемо и само показывает направление зависимости, поэтому стрелки не нужны. Рёбра стали кривыми, чтобы длинные связи не шли сквозь колонки по прямой.

Несвязанные части графа, например C# и Go, идут друг под другом, узлы без рёбер — сеткой внизу. Колонка выше экрана складывается вбок с сохранением порядка: иначе на самоанализе колонка глубины 0 не влезла бы. Короткий граф растягивается по высоте страницы, не больше чем втрое.

Узлы меньше. Экранный размер при отдалении сохраняется лишь до половины строки раскладки, поэтому узлы не могут наехать друг на друга при любом масштабе. Проверено счётом пересечений и скриншотом страницы с реальными facts в тёмной теме: 0 наложений на 17 модулях и 267 типах.

## D-045. Типы показываются по выбранному модулю

Общий граф всех типов убран: на самоанализе 806 рёбер сливались в один пучок. Уровень Types теперь всегда про конкретное место. Клик по модулю показывает его типы и линии к большим узлам других модулей, клик по такой линии или по ребру графа модулей показывает только связи типов между двумя модулями, в двух колонках и с цветом по модулю. Кнопка Types недоступна, пока модуль не выбран. Клик по типу открывает код, клик по модулю теперь ведёт к его типам: файл модуля был бы произвольным первым файлом.

Члены типов сворачиваются в свой тип. У свободной функции типа нет, она рисуется малой точкой, если у неё есть связи: иначе между пакетами Go почти ничего бы не осталось. Рёбра `import` связывают модули и видны только в графе модулей; раньше этот граф их терял.

Ребро теперь одно на вид связи, цвет задан видом из контракта, параллельные рёбра расходятся веером. Цикл стал пунктиром: красный цвет занял бы место вида. Форма узла следует из `kind` и `isAbstract` в facts: круг — класс, треугольник — абстрактный класс, ромб — интерфейс, протокол и трейт, квадрат — структура, скруглённый квадрат — запись, шестиугольник — перечисление, пятиугольник — остальное, набор открыт. Контракты не менялись.

## D-046. Расширение для любого проекта: встроенные анализаторы, `nomos.json` необязателен

Расширение запускалось только в папке с `nomos.json`, а команды в нём указывали на исходники этого репозитория (`dotnet run --project analyzers/...`). На чужом проекте (FigureLibruary) панель показывала «0 findings», хотя анализ не запускался: `readWorkspace` падал с ENOENT. Сгенерированный `nomos.json` не помог бы: у пользователя нет исходников анализаторов.

Решение:

- **Анализаторы едут в пакете.** `npm run package -- --target <платформа>` (`extension/scripts/package.mjs`) собирает `.vsix` под одну платформу VS Code. Go — статический бинарник под цель (около 5,6 МБ). C# — сборка, зависящая от фреймворка (`UseAppHost=false`, без сателлитных ресурсов, около 10,5 МБ): одна на все платформы. Self-contained отвергнут: 70–90 МБ на платформу. Пакет win32-x64 — 6,6 МБ в сжатом виде.
- **Среда .NET — от расширения .NET Install Tool** (`ms-dotnettools.vscode-dotnet-runtime`, команда `dotnet.acquire`), его же используют расширения C#. Оно не объявлено в `extensionDependencies`: пользователю только с Go оно не нужно. Расширение предлагает установить его, когда в папке нашлись файлы анализатора, которому нужна среда; отказ даёт сообщение с причиной, остальные анализаторы работают.
- **Реестр `bundle/analyzers.json` — данные, а не код.** Язык, команда с подстановками `${bundle}` и `${runtime}`, `files`, описание среды. Его пишет скрипт сборки; языки названы только там (скрипт не входит в пакет, `check-boundary` его не проверяет). `src/core/bundle.ts` читает реестр и языков не знает.
- **Manifest 1.2.0: необязательное поле `files`** — шаблоны файлов, которые анализатор читает. Минорная версия: поле необязательное. Скрипт сборки копирует его в реестр, чтобы выбрать анализатор, не запуская его: иначе ради `manifest` C# пришлось бы ставить .NET в проекте без C#. Какие из подходящих файлов анализировать (`bin`, `vendor`, сгенерированные), решает по-прежнему анализатор.
- **Папка без `nomos.json`** получает те встроенные анализаторы, для которых `findFiles` нашёл хотя бы один файл по `files`. Они запускаются без `--config`; рабочая папка — `globalStorage` расширения, так что `.nomos/<язык>.sarif` не появляется в проекте. Если `nomos.json` есть, используется только он, как раньше.
- **Строка состояния** без единого запланированного анализатора пишет «nothing to analyze», а не «0 findings».
- **Новая зависимость:** `@vscode/vsce` 4.0.0 (dev) — упаковка `.vsix`. 4.1.0 вышла за неделю до решения, взята предыдущая. Её `postinstall` (`@vscode/vsce-sign`) нужен только для подписи при публикации, npm его не запускает до `npm install-scripts approve`. `npm audit` показывает две moderate-записи: `minimatch <11.0.1` (GHSA-g3hv-75wg-m249) внутри `vsce`; шаблоны ему даём только мы, в пакет он не попадает (`npm audit --omit=dev` — 0), исправленной версии `vsce` нет на 2026-11-03.

Проверено вручную: установленный `.vsix` в VS Code на FigureLibruary ставит .NET Install Tool, получает .NET 10 и показывает анализ без `nomos.json`. Первая попытка упала с `spawn ... dotnet.exe ENOENT`: VS Code не создаёт `globalStorage` расширения, а Node сообщает об отсутствующей рабочей папке как об отсутствующей программе. `launchConfig` теперь создаёт папку, а `runner` при отсутствующем `cwd` называет настоящую причину. e2e на папке без `nomos.json` (`npm run e2e -- <папка>`) написан, но не запускался: на машине висело обновление VS Code.

Не сделано: настройка (слои, пороги, парадигмы) в проекте без исходников Nomos. `command` в `nomos.json` обязателен, а путь к встроенному анализатору меняется с версией расширения; разрешить `nomos.json` без `command` — мажорное изменение контракта `nomos`, решать отдельно. Публикация в Marketplace требует своего `publisher`, лицензии и `repository` — это решение владельца; пока скрипт пакует с `--skip-license` и `--allow-missing-repository`.

## D-047. Вид связи — в линии, направление — в плавнике, связи узла — списком

На графе было не понять, кто кого наследует или вызывает: стрелок не было (D-044 полагался на то, что зависимости лежат слева), все линии были одной толщины и различались только цветом, а оранжевый `call` и розовый `inheritance` на тёмном фоне почти сливались. На плотном графе (`Nomos.Core`, 68 рёбер) направление и вид связи терялись совсем.

- **Вид связи — в начертании линии.** `inheritance` — толстая сплошная, `call` — сплошная, `type-ref` — пунктир, `import` — точки. Цвет остаётся вторым признаком.
- **Направление — «плавник» в середине линии:** две короткие наклонные черты острием к тому, что наследуют, вызывают или используют. Одинаковый для всех видов и маленький, чтобы не спорить с начертанием. У цели стрелку закрывала бы подпись, а у узла с десятками входящих связей они сбились бы в кучу. Первый вариант с полым треугольником, закрашенной и открытой стрелкой по UML пользователь счёл слишком крупным.
  Плавник той же толщины, что и его линия.
- **Имена типов на линии к свёрнутому модулю.** В режиме типов другие модули свёрнуты в один узел, и было не видно, какой их класс вызывают или наследуют. `buildFocus` теперь кладёт в ребро `via` — короткие имена типов на дальнем конце: для исходящей связи — то, к чему обращаются, для входящей — кто обращается. Они пишутся над плавником мелким полупрозрачным шрифтом (два имени и «+N»), полностью — в подсказке линии и в панели связей («inherits → FigureLibruary.Interface: ITriangle»). Если таких линий больше 12, имена видны только у связей узла под курсором, иначе на плотном графе они сливаются в фон. Параллельные линии разведены шире (16 вместо 12), чтобы их имена не наезжали.
- **Цикл — красная подложка под линией**, а не пунктир: пунктир теперь означает `type-ref`.
- **Легенда видов — переключатели.** Можно скрыть, например, `call` и `type-ref` и оставить одну иерархию наследования. Выбор сохраняется при переходе между модулями и типами.
- **Панель связей.** При наведении на узел справа внизу появляется список его связей, по одной в строке: «inherits → ITriangle», «called by ← TestTriangle (2)». Сначала исходящие, потом входящие, внутри — по виду и имени; скрытые виды не показываются.
- **Подписи под узлами**, по центру: справа от узла их пересекали приходящие связи, читать было тяжело. Строка раскладки выросла с 34 до 50, узел не больше 15, шрифт подписи не больше остатка строки, поэтому подпись не достаёт до узла следующей строки при любом масштабе.
- Разметка страницы вынесена в `src/ui/graphPage.ts` без зависимости от `vscode`, чтобы страницу можно было отрисовать вне редактора. Путь к `graph.js` раньше проходил через `asWebviewUri` дважды, теперь один раз.

Проверено скриншотами страницы с реальными facts (FigureLibruary и `analyzers/csharp/src`) в тёмной и светлой темах, с имитацией наведения и фильтра. В настоящем VS Code не проверено. Контракты не менялись.

## D-048. Длинные связи обходят узлы, свои полосы у связей узла, скобки для циклов, имена вдоль линии

- **Длинная связь обходит чужие узлы.** Связь через несколько колонок шла по прямой кривой и проходила сквозь узел, стоящий у неё на пути: на FigureLibruary в типах `Interface` связь Figure → IFigure (через Circle) шла сквозь ITriangle, и казалось, что две связи сливаются в ITriangle и расходятся вновь. Теперь, как в классической послойной раскладке, такая связь получает невидимую опорную точку в каждой пересекаемой колонке. Точки упорядочиваются вместе с узлами и занимают в колонке узкий слот (18 вместо строки 50), поэтому у связи своя дорожка. После расстановки опорные точки выпрямляются: каждая тянется к середине между соседями по маршруту, сохраняя порядок в колонке и зазоры до соседних узлов и точек, так что на узел она не заходит. Кривая проходит через них сплайном Катмулла — Рома; касательные у всех точек маршрута одного масштаба (на узлах — горизонтальные, длиной в крайний пролёт), поэтому дуга над симметричным маршрутом симметрична. Первый вариант, без выпрямления и с ручками разной длины на узлах и в точках, давал кривые дуги. Свёртка высокой колонки считает только узлы, опорные точки свёрнутой колонки идут между её первыми подколонками.
- **Колонка сворачивается только с 12 узлов.** После того как строка выросла до 50, порог упал до 6, и колонка глубины 0 на графе модулей Nomos (9 модулей) сворачивалась в две подколонки: модули одной глубины стояли рядом и читались как разные глубины, а связи к нижней половине колонки обходили её большими дугами.
- **Связи внутри одной колонки — скобки слева от неё.** Такие связи бывают только в цикле (Abstractions ↔ Abstractions.Ir, SuppressionFilter ↔ FileDirectives). Прежде они шли S-петлёй сквозь колонку или горизонтальным пучком. Теперь каждая — скобка слева, где связей меньше всего (у глубины 0 их нет вовсе); скобки одной пары вложены друг в друга с шагом полосы, порядок — по виду и номеру ребра. Порядок полос у узла тоже доопределён номером ребра, чтобы параллельные связи одного вида шли в одном порядке на обоих концах.
- **Связи одного узла больше не лежат друг на друге.** Раньше все линии сходились в центр узла, и у узлов с десятками связей (`AnalysisEngine`, `Nomos.Analyzer.CSharp`) было не понять, откуда и куда идёт линия. Теперь у каждого конца связи своя полоса: связи, уходящие с одной стороны узла, упорядочены по высоте узла на другом конце и разведены на 14 единиц (всего не больше трёх строк раскладки); пользователь счёл первые 9 слишком тесными. Линия начинается чуть в стороне от центра, внутри узла, и сразу уходит в свою полосу. Порядок по высоте другого конца убирает пересечения возле узла, а параллельные связи разных видов идут в одном порядке на обоих концах. Прежний веер параллельных связей (D-047) этим заменён.
- **Имя типа идёт вдоль линии**, над ней, и никогда не переворачивается; шрифт меньше (8,5 вместо 10). Горизонтальная подпись перекрывала наклонную линию.
- **Вкладка «Paradigms and Skipped Rules» свёрнута по умолчанию** (`"visibility": "collapsed"`): она отвечает на вопрос «почему по модулю нет находок» и нужна редко, но пользователь решил её оставить; ручное раскрытие VS Code запоминает.
- **Значок остаётся прежним** (три узла и три ребра) и больше не временный. Пробовались «n» внутри него и граф в форме буквы N; пользователь вернул исходный.

Проверено скриншотами с реальными facts. Контракты не менялись.

## D-049. План после выпуска: практики, русский язык, диаграмма классов, шесть новых языков

Пользователь попросил четыре функции и разрешил самому расставить этапы. Смысл трёх уточнён у него:

- **«Модель для выбора практик»** — профиль практик, который пользователь отмечает сам: именованные наборы правил из spec. Не подсказка по коду и не языковая модель: вывод остаётся детерминированным, внешних служб нет.
- **«Русский язык»** — интерфейс расширения, отчёты `ci`, тексты правил и находок. Не разбор кириллических идентификаторов.
- **«UML»** — диаграмма классов. Диаграммы пакетов и последовательности отложены и записаны в ROADMAP, раздел «Отложено».

**Этапы.** 10 — профиль практик, 11 — русский язык, 12 — диаграмма классов, 13–18 — TypeScript и JavaScript, Python, Java, Kotlin, Ruby, C++. Этап 9 (выпуск) остаётся текущим. Почему так:

- Этапы 10–12 меняют контракты (`nomos` 1.1.0, `rule` 1.1.0, профиль SARIF, facts 1.3.0). Если сделать их до языков, каждый новый анализатор реализует их сразу, а дорабатывать придётся только C# и Go.
- Практики раньше перевода: они добавляют строки интерфейса, которые этап 11 переведёт вместе с остальными. После этапа 11 строка без русского текста не проходит `check-l10n`, поэтому интерфейс диаграммы классов пишется сразу на двух языках.
- Языки — по отношению аудитории к стоимости. TypeScript и JavaScript работают на Node самого VS Code и не требуют от пользователя своей среды. Python и Java — большие аудитории со зрелыми родными средствами. Kotlin идёт после Java, потому что делит с ним JVM. Ruby — меньшая аудитория. C++ последний: препроцессор, флаги сборки и нативный анализатор под каждую платформу.

**Проектные решения в плане**, подтверждаются в начале своего этапа:

- Правило, выключенное выбором практик, получает в `skippedRules` существующую причину `disabled-by-config`, а не новую: новое значение перечисления — мажорная версия facts. Сообщение называет практики.
- Переводы находок — через `message.id`, `message.arguments` и `rule.messageStrings` из SARIF 2.1.0, с шаблонами в spec. Анализатор не знает локали, поэтому вывод одинаков при любом языке интерфейса; `message.text` остаётся английским запасным вариантом.
- Связи UML не требуют нового вида рёбер: обобщение и реализация различаются по `kind` и `isAbstract` цели ребра `inheritance`, ассоциации — по новым членам типов. Новый вид в перечислении `dependencies[].kind` был бы мажорной версией.
- Один анализатор на TypeScript и JavaScript, но два языка в реестре: в manifest и facts язык один.

Открытые вопросы 11–15 добавлены в список выше. Код и контракты этой записью не менялись.

## D-051. Этап 9: профиль практик

Ответы пользователя в начале этапа: практики нарезаются по темам, а не по категориям spec, и выбирают только находки.

- **Каталог** — `spec/practices.yaml` по новому контракту `practice` 1.0.0: id, название, описание, правила. Одиннадцать практик: `solid`, `simplicity` (DRY, KISS, YAGNI, Деметра), `clean-code`, `oop`, `functional`, `structural`, `architecture`, `maintainability`, `performance`, `patterns`, `security`. Правило может входить в несколько практик: God class и Feature envy (DSN004, DSN005) — и в `architecture`, и в `oop`. В отличие от плана D-049, практика перечисляет правила явно, без ссылок на категории: иначе разворачивать категории пришлось бы в C#, Go и расширении. Цена — новое правило нужно вписать в практику руками, поэтому `npm run validate` требует, чтобы каждое правило входило хотя бы в одну практику и каждый id существовал.
- **`nomos.json` 1.1.0: необязательное `practices`.** Нет поля — работают все правила, как раньше. Пустой список — не работает ни одно. Явное `rules.<id>.enabled` сильнее практики в обе стороны. Незнакомая практика — ошибка входа, код 3.
- **Пропуск — `disabled-by-config`** на весь запуск, с сообщением «Rule belongs to practice clean-code, which is not selected; 'practices' in nomos.json selects them», одинаковым в C# и Go. Новая причина потребовала бы мажорной версии facts. Если правило выключено ещё и парадигмой или `--rules`, запись одна, с прежним сообщением.
- **Метрики и балл.** Facts, граф и CodeLens от практик не зависят. Балл, как и раньше, считается по категориям правил, которые запускались: категория, все правила которой выключены практиками, в балл не входит. Отдельной логики для практик в балле нет.
- **Каталог в анализаторах и расширении.** C# встраивает `spec/practices.yaml` (`SpecPractices.cs`). Go и расширение получают JSON из нового `npm run spec-json` (`go-rules` оставлен тем же скриптом): `analyzers/go/internal/analyzer/practices.json` и `extension/practices.json`. `npm run validate` сверяет все созданные из spec файлы.
- **Расширение.** Команда «Nomos: Choose Practices» (значок в заголовке дерева находок) показывает каталог с галочками. В папке с `nomos.json` выбор после подтверждения записывается в его `practices`: файл переписывается с отступом в два пробела, версия 1.0.0 поднимается до 1.1.0. В папке без `nomos.json` выбор идёт в настройку `nomos.practices` папки (D-050). Тогда расширение пишет в своё хранилище файл рабочей области (`workspaces/<хеш папки>-<язык>.json`, команда анализатора и `practices`) и передаёт его через `--config`. Выбор всех практик сохраняется как отсутствие поля, чтобы практики следующих версий тоже были включены. Изменение настройки запускает анализ, подсказка строки состояния называет практики каждой папки.
- **Harness.** Правило, выключенное конфигурацией, больше не обязано иметь запись `missing-input`: оно не запускается, и вход ему не нужен. Раньше это не проявлялось, потому что ни один случай не выключал DSN003 или MNT004.
- **Случай `practices`**: выбрана `security`, SEC001 выключено явно, на обоих языках. SEC003 сообщает, SEC001 и CC003 молчат, хотя пароль в коде и шесть параметров есть. CC003, DSN001 и SEC001 записаны как `disabled-by-config`.

Проверено: `dotnet test` (201), `go test`, harness (44 из 44, `selftest`), `ci`, тесты расширения (27) и `check-boundary`. В настоящем VS Code команда и настройка не проверялись, e2e не запускался.

## D-052. Этап 10: русский язык интерфейса и находок

Ответы пользователя в начале этапа: переводятся и сообщение, и объяснение находки; язык следует языку VS Code, своей настройки нет; устоявшиеся термины пишутся «по-русски (English)», аббревиатуры SOLID, DRY, KISS, YAGNI — как есть. Проектное решение D-049 (ключ и аргументы в SARIF, шаблоны в spec, анализатор не знает локали) подтверждено. Формат шаблонов и границы перевода — `spec/l10n.md`.

- **Контракты.** `rule` 1.1.0: необязательные `l10n.ru { title, description, rationale }` и `messages { ключ: { text, ru } }` — сообщения и объяснения в одном словаре. `practice` 1.1.0: `l10n.ru { title, description }`. Профиль SARIF 1.1.0: `rule.messageStrings` с английскими шаблонами, `message.id` и `message.arguments`, `properties.explanationMessage { id, arguments }`. Поля обязательны, если у правила в spec есть `messages`, иначе перевод был бы неполным без ошибки. Facts не менялся.
- **Русские формы слов.** SARIF знает только `{n}`, а русскому нужны «1 строка, 2 строки, 5 строк». В переводах разрешено `{n|одна|две|пять}`: форма по числу аргумента n. Английские шаблоны его не используют, `npm run validate` это проверяет. Форматирование написано трижды — в расширении, в `ci` и в `graph.js`, который ничего не импортирует; синтаксис общий и проверен тестами в каждом месте.
- **Ключ находится по тексту.** Анализатор не пишет ключи руками: в C# `Report` принимает `FormattableString`, и `TemplateText` превращает интерполяцию в шаблон и аргументы (культура инвариантная, раньше была текущей). В Go `report` принимает `Text` из `tx(формат, …)`. SARIF-писатель ищет шаблон среди `messages` правила. Чтобы ветви без фикстур не остались без перевода, тест каждого анализатора читает исходники (Roslyn и `go/ast`) и требует, чтобы каждый текст был шаблоном своего правила, без английских слов и вложенных шаблонов в аргументах. Отвергнуто: ключи у места вызова (`M("lines", …)`) — английский текст ушёл бы из кода, а совпадение текста с golden-файлами пришлось бы проверять отдельно.
- **Английские слова в аргументах убраны.** Варианты текста стали отдельными шаблонами: зоны DSN001, `allowed: none` в DSN003, виды имён CS.NAM001, «a sequence» в ALG002. Список эффектов FUN001 записан кодом (`total = …`, `Console.WriteLine()`, `list.Add()`, `DateTime.Now`) вместо фраз — это единственное изменение текста находок, плюс исправленное «for a interface» → «for an interface» в CS.NAM001. Golden-файл SARIF C# изменился только добавлением полей; в него ни FUN001, ни NAM001 интерфейса не попадают.
- **Шаблоны C# и Go общие там, где тексты совпадают.** Где Go говорит иначе (struct вместо object, units вместо types), у правила два ключа. Сейчас у 59 правил 201 шаблон.
- **Расширение.** `core/l10n.ts` без `vscode`: переводчик по бандлу, шаблоны, перевод находок по `rules.json`, причины пропуска по коду `reason`. Для `disabled-by-config` расширение само называет невыбранные практики правила (оно знает выбор папки), остальные коды переводятся общей фразой, текст анализатора остаётся в английском интерфейсе. Признаки парадигм переводятся по виду (`oop.classes`…), имена парадигм — «ООП», «функциональная», «структурная»; в английском интерфейсе остаются id, как было. Ошибки запуска анализатора переводятся, нарушения контрактов — нет: они для автора анализатора. Имена метрик и id правил не переводятся. Строки графа собирает `ui/graphStrings.ts` и шлёт вместе с данными; `graph.js` своих слов не содержит. `package.json` получил `l10n` и `%ключи%` с `category: "Nomos"`, поэтому в палитре команды выглядят как раньше, а в подсказках кнопок теперь без префикса «Nomos:».
- **`ci --locale ru`** переводит отчёты; facts, SARIF, базовая линия и код возврата от языка не зависят. Базовая линия хранит английский текст, поэтому исчезнувшие находки в русском отчёте — по-английски.
- **Генераторы.** `npm run spec-json` пишет ещё `extension/rules.json` и `ci/rules.json`; `docs/ANALYZERS.md` показывает русские названия и описания, английское название — отдельной колонкой.
- **`npm run check-l10n`** (`extension`, входит в CI): каждая строка `t(…)` расширения и `ci` есть в русском бандле с теми же аргументами, в бандле нет лишних строк, все тексты `package.json` — ключи `package.nls`, у каждого правила, практики и шаблона есть русский текст. Строка, переданная в `t` не литералом, — ошибка проверки.
- **Проверка в настоящем VS Code на русском не автоматизирована.** `--locale=ru` в e2e VS Code игнорирует: языковой пакет, поставленный в профиль теста, не попадает в его `languagepacks.json`. e2e проверяет, что тексты находок и Diagnostics следуют языку интерфейса, и проходит на английском; русский проверен модульными тестами, снимками графа (`screenshot.mjs --locale ru`) и отчётом `ci --locale ru` по этому репозиторию (517 находок, все переведены).

Проверено: `dotnet test` (202), `go test`, harness (44 из 44, `selftest`), тесты harness на Node 22.18, `ci` (8), тесты расширения (29), `check-boundary`, `check-l10n`, e2e с `nomos.json` и без него.
