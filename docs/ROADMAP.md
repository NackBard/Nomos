# Дорожная карта

Порядок этапов определён в D-020. Этап считается завершённым, когда выполнены все пункты «Готово, когда». Чем раньше фиксируется контракт, тем дешевле каждый следующий этап: расширение и второй язык строятся против него.

Общее ограничение всех этапов: платформа даёт статистику. Пороги приёмки и вердикты не вводятся.

Состояние: все этапы 1–8 завершены (D-031, D-032, D-034, D-036, D-037, D-038, D-039). Открытые вопросы 1–11 закрыты (D-040, D-050). Этап 9 (профиль практик) сделан, D-051; осталась проверка глазами в VS Code. Текущая цель — этап 10: русский язык. Дальше (D-049, D-050): 11 — диаграмма классов, 12–17 — новые языки, 18 — выпуск расширения.

Порядок (D-049, D-050): сначала всё, что меняет контракты (этапы 9–11), потом языки. Тогда каждый новый анализатор с первого дня реализует практики, ключи сообщений и члены типов, и не приходится догонять старые. Языки идут по отношению аудитории к стоимости: TypeScript и JavaScript не требуют от пользователя своей среды, C++ — самый дорогой из-за препроцессора и флагов сборки. Выпуск — последним, когда всё это готово.

Как проверить, что всё на месте: `dotnet test Nomos.slnx` в `analyzers/csharp`; `npm run validate`, `npm test`, `npm run selftest`, `npm run all` в `conformance/runner`; `go test ./...` в `analyzers/go`; `npm test` в `ci`; `npm test`, `npm run check-boundary`, `npm run e2e` в `extension`. CI (`.github/workflows/ci.yml`) зелёный на `main`, он запускается на Ubuntu и Node 22.18 (D-035), его результат смотрит `gh run list`.

## Этап 1. Контракты, spec, conformance-harness

- `contracts/`: схемы manifest, facts, правила, nomos.json, conformance-case; профиль SARIF.
- `spec/`: `rules/*.yaml`, `metrics.md`, `paradigms.md`.
- `conformance/runner`: запускает анализатор, проверяет схемы, сравнивает facts с допусками, проверяет parity между языками.
- Первые случаи: `metrics-basic`, `coupling-martin`, `cycles`, `paradigm-evidence`.
- Валидация `spec/rules/*.yaml` по `rule.schema.json` в CI.

Готово, когда: схемы проходят метавалидацию; harness запускается на «пустом» анализаторе-заглушке и сообщает понятные ошибки; случаи имеют эталоны, посчитанные вручную по `spec/metrics.md`.

## Этап 9. Профиль практик

Цель: пользователь сам отмечает, какие практики ему нужны (SOLID, Clean Code, функциональный стиль, безопасность…), и видит находки только по ним. Это выбор того, что смотреть, а не порог приёмки: сырые метрики выводятся по-прежнему все.

- **Каталог практик в spec.** `spec/practices.yaml` и схема `contracts/practice.schema.json` 1.0.0: id, название, описание, состав — категории и отдельные правила из `spec/rules`. Правило может входить в несколько практик. Начальный набор: `solid`, `clean-code`, `functional`, `structural`, `design`, `algorithms`, `patterns`, `maintainability`, `security` и языковые (`csharp`). `npm run validate` проверяет, что каждое правило входит хотя бы в одну практику и каждый id существует.
- **`nomos.json` 1.1.0: необязательное поле `practices`** — список id. Нет поля — работают все правила, как сейчас; минорная версия. Явное `rules.<id>.enabled` сильнее практики.
- **Анализаторы.** Правило вне выбранных практик получает запись `skippedRules` с причиной `disabled-by-config` и сообщением, называющим практики: новая причина потребовала бы мажорной версии facts. Каталог доезжает до анализаторов так же, как тексты правил (`npm run go-rules` → общий генератор).
- **Расширение.** Команда «Nomos: Choose Practices» — список с галочками из каталога (данные из `bundle/`, расширение практик не знает), выбор хранится в настройке `nomos.practices` рабочей области. С `nomos.json` команда предлагает записать `practices` в него. Дерево и строка состояния показывают, какие практики включены.
- **Настройка без `nomos.json`** (открытый вопрос 11, D-050). Настройки VS Code рабочей области: сейчас `nomos.practices`, позже слои, пороги и парадигмы. Расширение собирает из них файл рабочей области с командами встроенных анализаторов в своём хранилище и передаёт его через `--config`. Контракт `nomos` не ломается; `ci` этих настроек не видит, для него по-прежнему нужен `nomos.json`.
- **Случай conformance `practices`** с `config`, эталон вручную; `ci` получает поле из `nomos.json` без доработок.

Готово, когда: выбор практик в VS Code меняет состав находок C# и Go без перезапуска редактора; выключенные правила видны в «Paradigms and Skipped Rules» с причиной; случай `practices` проходит на обоих языках.

Сделано, D-051: каталог из 11 практик по темам, контракты `practice` 1.0.0 и `nomos` 1.1.0, C# и Go, `npm run spec-json`, команда «Nomos: Choose Practices» и настройка `nomos.practices`, случай `practices`. Каталог перечисляет правила явно, без категорий. Не проверено в настоящем VS Code.

## Этап 10. Русский язык интерфейса и находок

Цель: при русском интерфейсе VS Code всё, что показывает Nomos, — по-русски; в остальных случаях — по-английски, как сейчас. Анализ от языка не зависит: вывод анализатора по-прежнему детерминирован и одинаков при любой локали.

- **Расширение.** `vscode.l10n` и `l10n/bundle.l10n.ru.json` для строк кода, `package.nls.json` и `package.nls.ru.json` для команд, представлений и настроек. Строки страницы графа приходят с хоста вместе с данными: `graph.js` их не содержит. `screenshot.mjs` получает `--locale ru`.
- **Тексты правил.** Контракт `rule` 1.1.0: необязательное поле `l10n: { ru: { title, description, rationale } }` в `spec/rules/*.yaml`; генераторы (`rules-doc`, тексты для Go) переносят его. Каталог практик — так же.
- **Тексты находок.** SARIF позволяет `message.id` и `message.arguments` с шаблонами в `rule.messageStrings`. Шаблоны на обоих языках лежат в spec рядом с правилом, анализатор выдаёт ключ и аргументы, а `message.text` и `properties.explanation` остаются английскими как запасной вариант. Расширение и `ci` подставляют шаблон нужной локали. Это изменение `contracts/sarif-profile.md` (поля необязательны) и обоих анализаторов.
- **Причины пропуска и диагностика.** Коды (`paradigm-not-detected`, `missing-input`…) переводятся по коду в расширении; текст анализатора остаётся запасным.
- **Отчёты `ci`**: `--locale ru`, по умолчанию английский.
- **Проверка полноты** `npm run check-l10n`: у каждой строки интерфейса, правила, практики и шаблона есть русский текст; входит в CI. С этого этапа новая строка без перевода не проходит проверку.

Готово, когда: в VS Code с русским языком меню, дерево, граф, подсказки, Diagnostics и находки C# и Go по-русски; при английском — без изменений; `check-l10n` зелёный в CI; golden-файлы изменились только добавлением `message.id` и `arguments`.

## Этап 11. Диаграмма классов UML

Цель: галочка «UML» на странице графа в режиме типов превращает узлы в классы UML с полями и методами, а связи — в обозначения UML; ту же диаграмму можно выгрузить текстом.

- **Facts 1.3.0, все поля необязательные:** `types[].members` — поля, свойства, события, константы (имя, вид, видимость, имя типа как в коде, id типа проекта, если он разрешён, признаки `static` и коллекции); `types[].typeParameters`; `functions[].parameters` (имя и имя типа) и `functions[].returnTypeName`. Смысл каждого поля и то, как из него получаются связи UML, определяет новый раздел spec (`spec/structure.md`): обобщение — `inheritance` к классу, реализация — к типу с `isAbstract` вида interface/protocol/trait, ассоциация — член типа проекта, с кратностью `*` для коллекции, зависимость — `type-ref` и `call` без члена.
- **C# и Go заполняют поля.** Для Go в spec решается, как изображать встраивание (композиция со стереотипом) и неявную реализацию интерфейсов (нужна проверка `go/types`; без неё связи нет).
- **Случай conformance `type-structure`**, эталон вручную, на обоих языках.
- **Расширение.** `src/core/uml.ts` без `vscode`: из facts строит модель диаграммы и текст PlantUML и Mermaid, порядок детерминирован. На странице графа — галочка «UML» в панели режима типов: прямоугольники класса с отделениями, знаки видимости `+ - # ~`, стереотипы `«interface»`, `«enum»`, связи UML. Длинные отделения сворачиваются в «+N». Обозначения UML крупнее плавника D-047, который пользователь выбрал вместо них; в режиме UML они — суть диаграммы, размер согласуется по скриншоту. Команда «Nomos: Export Class Diagram» сохраняет `.puml` или `.mmd` для выбранного модуля или пары модулей.

Готово, когда: галочка работает на типах модуля и на связях двух модулей для C# и Go, выбор переживает переход между модулями; выгруженный текст открывается в PlantUML и Mermaid без правок; случай `type-structure` проходит.

Нативный анализатор под каждую платформу и размер libclang в пакете — открытый вопрос 15. Последним: разбор и сборка здесь дороже, чем у любого другого языка списка.

## Этап 18. Выпуск расширения в общее пользование

Цель: любой человек ставит Nomos из Marketplace и видит анализ своего проекта на любом из поддерживаемых языков без исходников Nomos и без `nomos.json`. Перенесён в конец по решению пользователя (D-050): к публикации расширение приходит со всеми языками, практиками, русским языком и UML. Основа готова: анализаторы едут в пакете, `nomos.json` необязателен (D-046), граф читается без объяснений (D-047, D-048).

- **Издатель и правовая часть.** Свой `publisher` в Marketplace вместо заглушки `nomos`, лицензия вместо `UNLICENSED`, `repository`, `CHANGELOG.md`; значок 128×128 PNG для страницы Marketplace (`icon` в `package.json`) по рисунку `media/icon.svg`. Скрипт `package.mjs` перестаёт пользоваться `--skip-license` и `--allow-missing-repository`.
- **Пакеты под все платформы в CI.** Матрица `win32-x64`, `win32-arm64`, `linux-x64`, `linux-arm64`, `darwin-x64`, `darwin-arm64`, `alpine-x64`; каждый пакет проверяется запуском встроенных анализаторов на платформе, для которой собран.
